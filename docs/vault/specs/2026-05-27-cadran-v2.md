# Spec — Cadran v2 — sélection par couche & cartes contextuelles

## Vision

Le Cadran est la visualisation centrale de Nightfall : trois anneaux concentriques sur un cadran 24 heures — sommeil (externe), usage écran (milieu), déplacements (interne). Sa mission produit est de rendre visible, en un coup d'œil, la corrélation entre exposition lumière artificielle (écran), activité physique / sorties / soleil, et qualité du sommeil — les deux leviers connus du drift circadien et de son recadrage dans le Non-24.

La v1 souffre de trois problèmes structurels : (1) la sélection par quadrant de 6 heures est trop grossière pour être utile ; (2) l'anneau usage est sémantiquement incorrect — il concentre l'intégralité du temps foreground d'une app dans le seul bucket de `lastTimeUsedMs`, colorant ainsi des heures de sommeil où le téléphone n'était pas utilisé ; (3) le compteur central "déplacements" additionne à tort `visits` (lieux statiques) et `activities` (segments de mouvement), ce qui est numériquement incohérent.

La v2 corrige ces trois problèmes et introduit une interaction à deux niveaux (anneau puis segment) cohérente avec la sémantique des données, tout en déclarant explicitement ses dépendances data-layer non encore livrées (`usage-sessions`, `labeled-places`).

---

## Périmètre de cette spec

Cette spec couvre exactement une PR : l'interaction + les cartes contextuelles + le correctif compteur + l'interface carte déférée. Elle ne couvre pas :
- le pipeline de collecte des sessions d'usage intra-journée (spec `usage-sessions`, Phase B_us)
- la configuration et la résolution des lieux labellisés (spec `labeled-places`)
- le basemap interactif pour la carte des trajets (décision ultérieure, interface déférée documentée ici)

## Dépendances déclarées

| Spec dépendante | Slug | Phase | Rôle dans cette spec |
|---|---|---|---|
| Sessions d'usage intra-journée | `usage-sessions` | B_us | Fournit `UsageSessionEntity` (startMs/endMs/packageName) pour que l'anneau usage affiche des segments aux horaires réels. Sans elle, l'anneau usage reste en état dégradé (placeholder grisé + mention "données indisponibles"). |
| Lieux labellisés configurables | `labeled-places` | B_lp | Fournit la liste des lieux connus (domicile, travail, famille, vacances…) avec coords + rayon, pour la logique binaire "ancré / déplacement" de l'anneau timeline. Sans elle, l'anneau timeline affiche tous les lieux sans distinction d'ancrage. |

**Règle d'état dégradé** : l'anneau concerné par une dépendance absente s'affiche en grisé uniforme avec un texte court dans la carte contextuelle ("Sessions d'usage non encore collectées — importer via Paramètres"). L'appli ne crashe pas, la navigation reste fonctionnelle.

## Problèmes actuels documentés

### P1 — Sélection quadrant 6h inutilisable

`hitTestQuadrant()` dans `MultiDonutClock.kt` (ligne 518–529) découpe le cadran en 4 tranches de 6h fixes (nuit/matin/après-midi/soir). Ces quadrants ne correspondent pas aux moments sémantiques de l'utilisateur (coucher, réveil, sortie, etc.). Toute la logique `selectedQuadrant: Int?` + `onQuadrantTap: (Int) -> Unit` + `QuadrantsCard` dans `RadialClockScreen.kt` est à remplacer.

### P2 — Anneau usage sémantiquement faux

Dans `RadialClockViewModel.kt` (ligne 127), `usageRows` est peuplé depuis `UsageDailyEntity` qui ne contient que des totaux quotidiens (`totalTimeForegroundMs`) et un `lastTimeUsedMs` (timestamp de dernière fermeture). Le `drawUsageHeat()` (MultiDonutClock.kt ligne 291) crée l'illusion d'une distribution horaire en plaçant tout le temps foreground d'une app dans le bucket de sa dernière heure d'utilisation. Ceci produit systématiquement des heures de sommeil colorées "actives".

La variante `UsageVariant.Apps` (ligne 316) aggrave le problème : elle trace un arc continu centré sur `lastTimeUsedMs` dont la largeur angulaire est proportionnelle au total foreground — un arc qui peut s'étendre sur plusieurs heures sans rapport avec les moments d'usage réels.

### P3 — Compteur central incohérent

Dans `CenterLabel` (MultiDonutClock.kt ligne 466) : `"${day.visits.size + day.activities.size} déplacements"`. Or `visits` sont des séjours statiques (lieux visités, `location_visits`) et `activities` sont des segments de mouvement (`activity_segments`). La somme est sémantiquement incorrecte et confuse pour l'utilisateur.

### P4 — Couleurs codées en dur (light mode cassé)

`MultiDonutClock.kt` contient plusieurs couleurs littérales (`Color(0xFF1E262B)` ligne 300, `Color(0xFF2E3D44)` ligne 323, `Color(0xFFE8EFF2)` ligne 335, `Color(0xFFF2F6F8)` dans `HourLabels` lignes 413–414, dans `CenterLabel` ligne 456) qui ignorent le mode clair. En light mode, le fond du canvas reste sombre et le texte blanc est illisible.

## Décisions techniques

### DT-1 — Modèle de sélection : remplacement de `selectedQuadrant`

Remplacer le paramètre `selectedQuadrant: Int?` par un état de sélection à deux niveaux :

```
enum class RadialLayer { SLEEP, USAGE, TIMELINE }

data class RadialSelection(
    val layer: RadialLayer,
    val segmentStartMs: Long? = null,   // null = couche entière sélectionnée
    val segmentEndMs:   Long? = null,
)
```

`selectedQuadrant` et `onQuadrantTap` sont supprimés de la signature publique de `MultiDonutClock`. Le nouveau paramètre est `selection: RadialSelection?` + `onSelectionChange: (RadialSelection?) -> Unit`.

`RadialClockScreen` déclare `var selection by remember { mutableStateOf<RadialSelection?>(null) }` et le passe au canvas.

### DT-2 — Hit-test radial à deux étages

Supprimer `hitTestQuadrant()`. Remplacer par une fonction `hitTestRadial()` qui :

1. Calcule la distance radiale du tap depuis le centre. Détermine dans quel anneau le tap tombe :
   - `rTimelineInner..rTimelineOuter` → `RadialLayer.TIMELINE`
   - `rUsageInner..rUsageOuter` → `RadialLayer.USAGE`
   - `rSleepDeepInner..rSleepOuter` → `RadialLayer.SLEEP`
   - hors de ces bornes → `null` (désélection)

2. Calcule l'heure du tap (0.0..24.0) depuis l'angle, identique à la logique actuelle de `hitTestQuadrant`.

3. Si la couche tappée est la même que `selection?.layer`, cherche le segment précis (StageInterval / RadialVisit+RadialActivity / UsageSession) qui contient l'heure tappée. Si trouvé → `RadialSelection(layer, segment.startMs, segment.endMs)` (Niveau 2 — détail). Si non trouvé ou anneau different → `RadialSelection(layer)` (Niveau 1 — vue globale couche).

4. Re-tap sur le même anneau en Niveau 1 sans segment, ou tap hors zone → `null` (désélection).

### DT-3 — Focus mode / dim

Quand `selection != null` :
- L'anneau sélectionné est rendu à opacité nominale.
- Les deux autres anneaux sont rendus à opacité réduite (`alpha * 0.35f`).
- Si un segment est sélectionné (`segmentStartMs != null`) : le segment précis est surligné (opacité 1.0 + liseré `accent-teal`), les autres segments du même anneau sont dimés (`alpha * 0.45f`).
- Re-tap / tap hors zone = `selection = null` → opacités nominales.

L'anneau actif avec le surlignage de segment remplace entièrement le `selectedQuadrant highlight` actuel (drawDonutWedge couleur secondaire alpha 0.10f, ligne 204–207 de MultiDonutClock.kt).

### DT-4 — Compteur central corrigé (P3)

`CenterLabel` adopte une métrique contextuelle selon `selection?.layer` :

| Contexte | Métrique affichée |
|---|---|
| Pas de sélection | durée sommeil (prioritaire) sinon durée usage ; pas de compteur "déplacements" |
| `SLEEP` sélectionné | durée sommeil + nb de sessions |
| `USAGE` sélectionné | temps écran total |
| `TIMELINE` sélectionné | nb de sorties (uniquement `activities` — pas `visits`) + km totaux |

La ligne `"${day.visits.size + day.activities.size} déplacements"` est supprimée.

### DT-5 — Anneau usage : état dégradé en attendant `usage-sessions`

Tant que `usage-sessions` n'est pas livré, `UsageDailyEntity` ne permet pas une représentation horaire correcte. Le comportement dégradé de la v2 est :

- Variante Heat : remplacée par un anneau grisé uniforme (`extras.divider.copy(alpha = 0.4f)`) portant un badge textuel "Sessions d'usage non collectées".
- Variante Apps : conservée à titre indicatif (liste des apps par total journalier, sans positionnement sur le cadran), mais l'arc horaire est supprimé.

Le toggle Heat/Apps est conservé mais le mode Heat ne colore rien tant que `UsageSessionEntity` n'alimente pas `RadialDay.usageSessions`.

**Anticipation** : `RadialDay` reçoit un champ `usageSessions: List<UsageSession> = emptyList()` (nouveau DTO à définir dans la spec `usage-sessions`). Tant que la liste est vide, état dégradé déclenché. `RadialUsageRow` conservé pour la liste apps (variante Apps).

### DT-6 — Anneau timeline : binaire ancré / déplacement

L'anneau timeline devient visuellement binaire :
- **Lieu ancré** (dans la liste `labeled-places`) : couleur `accent-amber` `#d37c04`, opacité 0.85.
- **Déplacement / activité** : couleur par type d'activité (palette `Activity` existante).
- **Lieu non labellisé** : couleur `extras.textMuted` (`#7a9aaa`), opacité 0.55 — signale qu'il n'a pas encore été qualifié.

En attendant la spec `labeled-places`, la résolution "ancré" se fait par le préfixe de `placeName` (logique `placeColor()` existante, conservée telle quelle comme approximation temporaire). La distinction visuelle amber vs couleur activité est cependant déjà en place dès cette PR.

### DT-7 — Interface carte déférée (`TrajetMapRenderer`)

Décision : aucun basemap ne sort des coordonnées dans cette PR (contrainte C1). La carte des trajets est déférée derrière une interface pluggable :

```kotlin
interface TrajetMapRenderer {
    @Composable
    fun Render(visits: List<RadialVisit>, activities: List<RadialActivity>, modifier: Modifier)
}

object NullTrajetMapRenderer : TrajetMapRenderer {
    @Composable
    override fun Render(...) { /* no-op */ }
}
```

La carte contextuelle Timeline affiche en v2 uniquement le rendu **texte** : lieux + horaires + distance + type. Un slot optionnel `mapRenderer: TrajetMapRenderer = NullTrajetMapRenderer` est prévu dans la signature de la carte contextuelle pour plugger un rendu canvas local ultérieur (tracé normalisé fond neutre, zéro fuite réseau). Tout basemap réseau (Google Maps, MapLibre avec tuiles externes) est une dérogation C1 explicite à documenter dans une spec future séparée.

### DT-8 — Tokens couleur : élimination des littéraux hardcodés (P4)

Tous les `Color(0xFF...)` littéraux dans `MultiDonutClock.kt` liés à des couleurs de fond/texte/séparateur sont remplacés par des références au `DataSaillanceTheme` :
- `Color(0xFF1E262B)` (case heat vide) → `MaterialTheme.colorScheme.surface` (résolu en dark = `#232e32`, light = `#f4f8fa`)
- `Color(0xFF2E3D44)` (empty band) → `extras.borderStrong`
- `Color(0xFFE8EFF2)` (sub-ring faint) → `MaterialTheme.colorScheme.onBackground.copy(alpha = 0.05f)`
- `Color(0xFFF2F6F8)` (labels heure, CenterLabel valeur) → `MaterialTheme.colorScheme.onBackground`

Les couleurs sémantiques des données (stageColors, Activity palette, heatColor ramp) conservent leurs valeurs — elles sont intentionnellement fixes. Seules les couleurs structurelles (fonds, séparateurs, textes) passent par les tokens.

### DT-9 — `RadialDay` : évolution du DTO

`RadialDay` reçoit un champ supplémentaire en prévision de `usage-sessions` :

```kotlin
data class RadialDay(
    val date: LocalDate,
    val sleepStages: List<StageInterval> = emptyList(),
    val visits: List<RadialVisit> = emptyList(),
    val activities: List<RadialActivity> = emptyList(),
    val usageRows: List<RadialUsageRow> = emptyList(),      // conservé pour la liste apps
    val usageSessions: List<UsageSession> = emptyList(),    // vide jusqu'à spec usage-sessions
)
```

`UsageSession` est un DTO minimaliste défini localement pour cette spec (il sera remplacé/aligné par la spec `usage-sessions`) :

```kotlin
data class UsageSession(
    val packageName: String,
    val startMs: Long,
    val endMs: Long,
)
```

## Cartes contextuelles

### Structure générale

Remplacer `QuadrantsCard` par `LayerContextCard`. La carte est pilotée par `selection: RadialSelection?`.

En l'absence de sélection (vue d'ensemble) : la carte affiche un résumé compact de chaque couche sur une ligne (voir DaySummaryCard actuelle, à consolider).

Quand `selection.layer` est défini sans segment (Niveau 1 — vue globale couche) : la carte expand la couche sélectionnée en vue détaillée globale.

Quand `selection.segmentStartMs != null` (Niveau 2 — détail moment) : la carte affiche le détail du segment précis.

### Carte Sommeil (`RadialLayer.SLEEP`)

**Vue globale (Niveau 1) :**
- Heure coucher (début du premier StageInterval non-AWAKE) et heure lever (fin du dernier)
- Durée totale sommeil (format `Xh YYmin`)
- Répartition des stages : barre proportionnelle colorée (StageStrip existant, à conserver) + pourcentages
- Nb de sessions (interruptions du sommeil)

**Détail segment (Niveau 2) :**
- Stage précis de l'intervalle sélectionné (AWAKE/REM/LIGHT/DEEP) avec sa couleur
- Durée du segment
- Position dans la nuit (ex. "3ème période de sommeil léger")

### Carte Usage (`RadialLayer.USAGE`)

**Vue globale (Niveau 1) :**
- Temps écran total (somme `totalTimeForegroundMs` depuis `usageRows`)
- Top 5 apps avec barre de durée (AppBarRow existant, conservé)
- Badge "Sessions horaires indisponibles" si `usageSessions.isEmpty()` — invite à importer via Paramètres

**Détail segment (Niveau 2) — disponible seulement quand `usageSessions` non vide :**
- App(s) actives dans la tranche sélectionnée
- Durée cumulée sur la tranche
- Contexte : avant/pendant/après une session de sommeil ?

### Carte Timeline (`RadialLayer.TIMELINE`)

**Vue globale (Niveau 1) :**
- Liste des visites : nom du lieu + heure arrivée → heure départ (format `HH:mm → HH:mm`) + durée
- Liste des activités : type (icône textuelle) + heure début/fin + distance en km
- Temps total de déplacement actif (uniquement `activities`, pas les visites statiques)
- Slot `mapRenderer.Render(...)` si le renderer est non-null et non-NullTrajetMapRenderer

**Détail segment (Niveau 2) :**
- Pour une visite : nom, adresse si disponible, durée précise, badge "lieu ancré" ou "lieu non labellisé"
- Pour une activité : type, durée, distance, heure début → heure fin
- Note : aucune coordonnée GPS affichée en clair dans l'UI (C2 — localisation = donnée de santé par corrélation)

| Usage | Dark | Light |
|---|---|---|

| Surface carte | `#232e32` (`--bg-panel`) | `#f4f8fa` |

| Texte secondaire | `#7a9aaa` | `#81868b` |
| Accent sélection | `#0e9eb0` (teal) | `#0e9eb0` |
| Accent lieu ancré | `#d37c04` (amber) | `#d37c04` |
| Accent highlight | `#3be5e7` (cyan) | `#3be5e7` |
| Bordure | `#2e3d44` | `#d0dde3` |

### Règles d'application spécifiques au Cadran

- L'anneau sélectionné : liseré `accent-teal` `1.5dp` en stroke sur les bords interne et externe de la bande
- Les anneaux dimés : `alpha * 0.35f` — la structure reste visible, pas invisible
- Segment sélectionné : liseré `accent-teal` `1dp` + opacité nominale
- Labels heure (minuit/6h/midi/18h) : `MaterialTheme.colorScheme.onBackground` — lisible en light ET dark
- Texte centre cadran : `MaterialTheme.colorScheme.onBackground` pour la valeur principale, `extras.textMuted` pour le label
- Police : `FontFamily.Default` (Roboto système) — pas de Playfair sur Android natif
- Tracking uppercase : `letterSpacing = 0.06em` minimum sur tous les labels en majuscules (déjà en place, à ne pas régresser)
- Interdit : `#6366f1`, gradients décoratifs, glows/halos, `box-shadow` décoratif

### Light mode

Le canvas Compose suit automatiquement `MaterialTheme.colorScheme` si les couleurs structurelles passent par les tokens (DT-8). Vérification obligatoire en light mode : contraste WCAG AA minimum sur les labels heure et la valeur centrale.

## Tests d'acceptation

### TA-1 — Tap anneau → focus mode

**Given** le cadran est affiché en vue d'ensemble (aucune sélection) et `day.sleepStages` est non vide.
**When** l'utilisateur tappe dans la bande de l'anneau externe (sommeil).
**Then** `selection.layer == RadialLayer.SLEEP`, `selection.segmentStartMs == null`. L'anneau sommeil s'affiche à opacité nominale. Les anneaux usage et timeline s'affichent à opacité réduite (alpha < 0.4). `LayerContextCard` affiche la vue globale sommeil (heure coucher/lever, durée, répartition stages). Aucune sélection de quadrant 6h n'est visible.

### TA-2 — Re-tap segment dans l'anneau sélectionné → détail

**Given** `selection.layer == RadialLayer.SLEEP`, aucun segment sélectionné.
**When** l'utilisateur tappe sur un segment de sommeil précis (par exemple un arc DEEP).
**Then** `selection.segmentStartMs` et `selection.segmentEndMs` sont non nuls. Le segment tappé est rendu à opacité 1.0 avec liseré teal. Les autres segments de l'anneau sommeil sont dimés. `LayerContextCard` affiche le détail du stage sélectionné (type, durée, position dans la nuit).

### TA-3 — Désélection par re-tap hors zone

**Given** une sélection active (`selection != null`).
**When** l'utilisateur tappe dans la zone centrale (hub) ou hors du cercle externe.
**Then** `selection == null`. Tous les anneaux reviennent à opacité nominale. `LayerContextCard` revient à la vue d'ensemble compacte.

### TA-4 — Désélection par re-tap sur l'anneau déjà sélectionné en Niveau 1

**Given** `selection = RadialSelection(RadialLayer.USAGE)`, aucun segment.
**When** l'utilisateur tappe à nouveau dans l'anneau usage sans viser un segment précis.
**Then** `selection == null`. Vue d'ensemble restaurée.

### TA-5 — Compteur central correct par couche

**Given** un `RadialDay` avec `visits.size == 3` et `activities.size == 2`.
**When** aucune sélection (vue d'ensemble).
**Then** le texte du centre ne contient pas "5 déplacements" ni aucune somme visits + activities. Le texte affiché est la durée de sommeil (si disponible) ou la durée usage, avec le label correspondant.

**When** `selection.layer == RadialLayer.TIMELINE`.
**Then** le centre affiche le nombre d'activités (segments de mouvement uniquement) et/ou les km totaux.

### TA-6 — État dégradé usage

**Given** `day.usageSessions.isEmpty()` (spec `usage-sessions` non livrée).
**When** l'utilisateur sélectionne l'anneau usage.
**Then** l'anneau usage s'affiche grisé (couleur uniforme `extras.divider`). `LayerContextCard` affiche la liste des apps (top 5 par total journalier) et un badge/texte "Sessions horaires non disponibles" distinct. Aucune exception n'est levée.

### TA-7 — Absence d'appel réseau / sortie de coordonnées (contrainte C1)

**Given** l'écran Cadran est ouvert avec des données contenant des coordonnées GPS (`lat`/`lng` dans `LocationVisitEntity`, `start_lat`/`end_lat` dans `ActivitySegmentEntity`).
**When** l'utilisateur navigue entre les jours, sélectionne tous les anneaux, ouvre tous les niveaux de détail.
**Then** aucun appel réseau n'est émis (vérifiable via test instrumenté avec `MockWebServer` ou assertion `OkHttp.Interceptor` zéro request). Aucune coordonnée GPS n'est affichée en clair dans l'UI. `NullTrajetMapRenderer.Render()` est appelé et ne produit aucune vue réseau.

### TA-8 — Light mode lisible

**Given** le thème système est en mode clair (`uiMode = Configuration.UI_MODE_NIGHT_NO`).
**When** le cadran est rendu.
**Then** les labels heure (minuit/6h/midi/18h) sont visibles sur fond clair. La valeur centrale est lisible. Aucune surface de canvas n'est `Color(0xFF1E262B)` (fond dark hardcodé). Ratio de contraste WCAG AA (4.5:1) respecté pour les textes de taille < 18sp.

### TA-9 — Changement de date réinitialise la sélection

**Given** une sélection active (`selection != null`).
**When** l'utilisateur appuie sur "précédent" ou "suivant" dans le `DateNavigator`.
**Then** `selection == null`. Vue d'ensemble affichée pour le nouveau jour. Aucun artefact visuel du jour précédent.

### TA-10 — Anneau timeline binaire (en présence de `labeled-places`)

**Given** la spec `labeled-places` est livrée et le domicile est configuré.
**When** une visite correspond à un lieu ancré (domicile).
**Then** le wedge de cette visite est affiché en `accent-amber` (#d37c04). Une visite hors liste est affichée en `extras.textMuted`. Un segment d'activité conserve sa couleur par type (Activity palette).

## Suite naturelle

### Prochaines specs à écrire (dans l'ordre)

1. **`usage-sessions`** (Phase B_us) — Spec data-layer pour `UsageStatsManager.queryEvents()` → `UsageSessionEntity` (startMs/endMs/packageName). Sans elle, l'anneau usage reste en état dégradé. Débloque L6 et TA-6 au niveau fonctionnel, et TA-2/TA-5 pour la couche usage.

2. **`labeled-places`** — Spec data-layer + écran de configuration des lieux labellisés (domicile, travail, famille, vacances…) avec coords + rayon. Doit gérer le cas multi-jours (séjour hors domicile = lieu ancré). Débloque TA-10 et la distinction visuelle amber/couleur dans l'anneau timeline.

3. **`trajet-map`** (Phase ultérieure, décision explicite) — Choisir un rendu pour la carte des trajets. Options **par ordre de préférence C1** :
   1. **Canvas normalisé local** (défaut recommandé) — tracé/points normalisés sur fond neutre, zéro fuite réseau, conforme C1 sans condition.
   2. **MapLibre avec tuiles auto-hébergées** — basemap géographique servi depuis l'infra contrôlée par l'utilisateur ; conforme C1 si l'hébergement reste sous contrôle.
   3. **Google Maps SDK** (recours de dernier ressort uniquement) — **dérogation C1 explicite** : à n'envisager que si 1 et 2 sont écartées, et seulement après décision documentée dans `VISION.md`/`NOTES.md` + consentement utilisateur traçable (C2). Envoie viewport/position à un tiers : à justifier, pas à acter par défaut.

   `TrajetMapRenderer` est l'interface de branchement prévue pour cette décision.

### Dépendances aval

- `RadialClockViewModel` devra être mis à jour pour charger `usageSessions` depuis le DAO `UsageStatsDao` une fois que la table `usage_sessions` existe (spec `usage-sessions`).
- `RadialDay.usageSessions` est la surface d'intégration : le ViewModel alimente, le canvas consomme, aucune logique business dans le canvas.
